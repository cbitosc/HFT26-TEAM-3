# INVESTIGATOR_UX_AUDIT

Audit at `main` 0774fe6, before the investigator-first redesign (branch `claude/investigator-ux`). Backend files were **read only**.

## 1. Current information architecture (before)
Workspace = three equal columns: left list (sources, actors, **every** event), centre (video, timeline with **every** event, trajectories, sensor), right tabs **Summary** (the stored per-event summary: five layers + uncertainty + open questions) / **Findings** (five kinds of finding cards) / **Evidence**. The default right panel is empty until an event is selected, and the first thing an investigator sees is 16–19 events, 8–31 findings, sensor charts and trajectories simultaneously. There is no case-level answer to "what appears to have happened".

## 2. Where displayed information comes from
| Item shown | Source | Generated by processing? |
|---|---|---|
| Video frames, boxes, track ids | `/overlays`, `/detections`, `/tracks` | **Yes**, from the detector/tracker run on the uploaded file, **or** boxes imported with `source: oracle` (synthetic world) / `external`. The model run id is `oracle:…`/`external:…` in that case; the UI did not surface it. |
| Machine events (slowing, stopped, enters/leaves, interaction, `possible_collision`, `possible_near_miss`) | `source_events` from `video_events.generate` over the stored tracks | **Yes**, deterministic rules over real tracks. Thresholds are heuristics (documented in RISKS R-35). Nothing is emitted without tracks. |
| Sensor events | `sensors.analyze` rules over the uploaded CSV with the investigator's mapping | **Yes**, deterministic. |
| Witness claims | `witness_claims` | **Reported** text. In the demo cases the claims were typed by `scenarios/loader.py` (manual extraction), not model output. LLM extraction exists but is policy-gated. |
| Identity ("Vehicle A") | `actor_links` | **Investigator decisions.** In the demo cases the loader confirmed them by matching the generator's own boxes (documented, R-36). |
| Clock relations | `sync_edges` / clock records | **Declared** by the investigator (demo: known generator offsets). Never inferred. |
| Contradictions / corroborations / inferences / gaps | `reconstruct.py` + `engine_rules.py` | **Yes**, rule-derived from the stored records; text is **templates filled with real values**. No language model writes any finding or summary today. |
| Event summaries | `rules.build_summary` | Templates from stored records. |
| Trajectories | `trajectories` | Image: tracked anchors. Ground plane: homography from investigator-entered calibration. |
| Confidence fields | `events.confidence` | Separate dimensions (source quality, timestamp basis, claim certainty). **There is no overall event or collision score**, and the UI never computed one. Box labels show the **detector's** score, which is not an event probability. |
| Demo content | `data/scenarios/*`, `scripts/seed_demo.py` | Entirely **synthetic**; labelled `synthetic` on the case and every evidence file. |

## 3. Hardcoded vs generated
- **Hardcoded in the backend app:** only template wording (`TITLES`, `GAP_ADVICE`, rule explanation strings, banned-language list). No event, track, detection, trajectory or finding is predefined in `backend/app`.
- **Hardcoded in demo tooling (synthetic, labelled):** the scenario videos and IMU files (`scenarios/world.py`), the claim annotations (`scenarios/loader.py` `CLAIMS`), pre-registered rule expectations in the evaluation script.
- **Hardcoded in the frontend:** landing-page marketing copy and explanatory captions. The landing hero timeline is fetched from the API.
- **No silent fallback to synthetic results exists.** A real upload whose detector finds nothing yields zero tracks and zero events (verified on the synthetic renders: 0 detections → 0 events).

## 4. Missing backend capabilities (requested, not invented)
1. **Case-level summary endpoint** (`GET /cases/{id}/overview`): headline, counts, significant events, provenance of the analysis. The frontend synthesises one (see §6) from stored records only; a backend version would be authoritative and testable.
2. **Event significance flag** (`significant: bool`, `significance_reason`): the frontend uses a documented list of event types.
3. **Finding structure:** explicit `classification` (observed | reported | inferred | unknown), `supporting_event_ids`, `contradicting_event_ids`, `interval`, `limitation`, `suggested_action`. Today these are derived client-side from `rule_id`, `basis`, `event_a/event_b`, `refs`.
4. **Analysis provenance per case:** which detector/tracker produced the boxes, versions, and whether real or imported (available via `/evidence/{id}/model-runs`; one call per video).
5. **Processing status summary** (analysed / partially analysed / not analysed per stage) beyond raw jobs.
6. **Per-event source row range** for sensor events and **nearest-frame lookup** (see handoff).
7. **Model-generated inferences do not exist.** All inferences are rule-based (`INF-BRAKE-PRIOR-01`). The UI labels them "inferred by rule".

## 5. New component hierarchy
```
Workspace
├─ NavRail (collapsible): Status · Sources · Vehicles · Key events
├─ Centre
│  ├─ Player (primary + secondary sources, overlays)  — unchanged integrations
│  └─ Timeline (key events by default; All events toggle; gap lane; finding focus band)
└─ Inspector (tabs)
   ├─ Overview      ← default: IncidentSummary · WhatWeFound · WhatIsUncertain · InvestigatorAttention
   ├─ Findings      ← FindingList → FindingDetail (8-part structure + "Details")
   ├─ Evidence      ← sources, statements, evidence for the selected finding (frame / statement / sensor drawers)
   └─ Technical     ← full event list · selected event layers · detection and tracking runs · confidence components · provenance · synchronization · gaps
```
Data flow: `lib/overview.js` (pure, tested) turns the API payloads into `{overview, findings[]}`; the store holds `selectedFindingId`, `highlightIds`, `focusRange`; selecting a finding seeks the player, highlights its events and interval on the timeline, selects the related vehicle, and updates the inspector.

## 6. Summary-generation data contract (frontend synthesis; backend may adopt)
Inputs (all existing endpoints): timeline events (+marks), contradictions, corroborations, gaps, findings, trajectories, actors, evidence (+video), seek targets, model runs, jobs.
Output `overview`:
```
headline: string                      // built only from collision/near-miss candidates and counts; says "appears"/"possible"
stats: {sources, trackedRoadUsers, significantEvents, contradictions, gaps}
analysis: {detection: 'real-detector'|'imported-synthetic'|'imported-external'|'none', models[], tracks, status}
found: Finding[3..5]                  // only findings backed by records, ranked by rule priority
uncertain: Finding[]                  // gaps, open questions, structural limits (contact unconfirmable from boxes; sync not established)
attention: {text, action, findingId?}[≤5]
```
`Finding`: `{id, kind, title, summary, classification, interval, supporting[], contradicting[], uncertainty, action, technical{text, ruleId, refs}, actorIds, priority, reviewId?}`.
Rules: a sentence is produced only from fields present in the records; an absent field omits the clause (never a guess); a count of zero is shown as zero; if no detections/tracks exist the overview says video analysis produced no tracked objects and does not describe movement.
Classification: `observed` = machine detection or sensor reading; `reported` = witness claim; `inferred` = rule-derived comparison or inference; `unknown` = gap or open question.
Confidence: no percentage is presented as the probability of an event. Detector scores are labelled "detector score"; event confidence is shown only as its separate components under Technical.

**Found during verification (fixed):** the first Overview called a case "boxes from a real detector" although its tracks came from imported synthetic boxes (an earlier real-detector run on the same video had stored 0 boxes). Provenance now uses the latest completed detection run per video, which is the run tracking consumes, and lists the others. Mobile layout overflowed horizontally in the Technical tab (grid item min-content); fixed.
**Limits:** the overview is synthesised in the browser from stored records, not by the backend (see §4.1); "significant event" is a frontend list; plain-language phrasing exists for the current rule ids only, other rules fall back to the backend's own text.
